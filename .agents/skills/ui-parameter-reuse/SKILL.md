# UI 参数复用与业务边界

## 核心约定

**UI 相似时共享结构，内容差异通过参数传入；业务行为相同才共享实现。**

- 用户指定已有 UI 为基准时，先找到其真实组件与调用方式。例如指定“图3角色库 Card”，应复用该 Card；如它绑定了角色业务，抽取稳定的展示部分，再由角色库和其他调用方共同使用。
- 复用应体现在调用关系：多个场景实际引用同一组件或方法。复制 JSX、样式或请求代码，再分别改名，不算复用。
- 不为每个功能组手写同构组件。输入参数结构与执行契约相同、仅配置不同的组，共用参数化 UI；流程也完全一致时，共用执行方法。
- 共同展示不等于共同业务，不因名称、按钮外观或返回字段相似就合并业务规则。
- 在本次授权范围内完成相关调用方接入。不得擅自把局部复用任务扩展为全仓库重构。

## 开发前判断

先搜索现有基准组件、相似实现及其使用处，阅读实际输入、状态、事件和副作用，再决定复用层级。不要仅凭截图或文件名创建新抽象。

| 现状 | 应采取的方式 |
| --- | --- |
| 已有组件满足要求 | 直接传入数据、状态与回调 |
| 布局与交互相同，仅文案、资源或动作不同 | 共享 UI，通过参数或动作配置注入 |
| 主体相同，局部内容不同 | 复用主体，以局部插槽或组合组件承载差异 |
| 输入契约、执行顺序、校验、错误及副作用全部相同 | 复用同一功能方法，以参数表达真实差异 |
| 内容来源不同，但获取、转换或分页机制相同 | 提取共同获取机制，各来源适配器保留其规则 |
| 仅 UI 相似，业务权限、落盘或后续动作不同 | 共用 UI，分别注入各自业务方法 |
| 只部分机制相同 | 仅提取已证明相同的部分，剩余逻辑由各业务组合 |
| 没有稳定共性 | 保持独立；不为预想中的未来复用建立框架 |

方法名相同、签名相同或返回字段相同，都不足以证明功能完全相同。对修改数据的方法，还要核对作用对象、权限、持久化、事件通知、撤销和失败后的恢复。

## 参数化 UI 的实现规则

1. **以既有规范为源。** 共享字号、间距、圆角、图片比例、选中态、悬停态与键盘行为；业务页面不复制整套样式进行微调。
2. **注入最小展示模型。** 只传 UI 需要的字段；若多个领域数据形状不同，在各自边界适配成统一模型，保留原始业务身份。
3. **显式传入状态。** 选中、禁用、加载、空态、错误和操作状态应有清晰契约；不得因共享组件让不同实例的状态相互污染。
4. **以回调表达动作。** 组件通知打开、选择、删除等用户意图，外部绑定真实业务；不在公共 Card 内根据业务类型决定删除哪个仓库。
5. **以插槽表达局部差异。** 少量区域不同可以组合实现；优先保留统一外壳，不把整个页面作为一个不受约束的插槽而只剩空封装。
6. **以配置表达同构功能组。** 配置传标题、字段定义、值、可用状态和动作；渲染器与共同交互只维护一份。若同一表单契约已经存在，应直接复用，不重复设计字段系统。
7. **变化必须有语义。** variant 只表示稳定的尺寸或布局差异。避免连续添加 `isCharacter`、`isWorkflow` 等开关，把多个业务页面塞进一个组件。

不要依赖调用方覆盖内部 DOM 选择器来保持外观，也不要用任意 `className` 差异掩盖同一 Card 的样式分叉。允许必要的布局扩展，但共享规范应由公共组件维护。

## 功能与内容获取的边界

- 业务逻辑只有行为契约完全一致时才合并；相似但不同的部分留在各自业务模块。
- 内容获取可以复用相同的请求编排、响应校验、分页或纯转换机制；不同来源的鉴权、参数映射、失败语义与缓存策略保留在适配层。
- 获取内容通常不应承担删除、安装、生成、写入配置等动作。不能把不同副作用统一命名为“内容获取”来扩大复用范围。
- 回调注入可让一个 UI 服务不同业务，不意味着这些回调必须收敛成一个通用业务方法。
- 共用方法不等于共用状态；缓存键和请求状态须覆盖来源及全部影响结果的参数，避免跨组串数据和过期响应覆盖。
- 复用仍遵守当前项目架构。Electron/Next.js 项目不得为共用代码跨越主进程、preload 和渲染进程边界，也不改变既有 i18n 和存储契约。

需要设计 Card、功能组参数，或判断两个方法是否应合并时，参阅 [具体场景与参数契约](references/reuse-examples.md)。其中名称只用于说明，必须先核对当前项目真实组件，不直接创建同名替代品。

## 提取与接入

以能服务当前调用方的最小公共部分开始。已有基准组件绑定业务时，先分离展示与适配，再让原入口继续使用公共展示，避免产生“旧基准一份、新通用组件一份”。

在授权范围内逐一接入同类功能组，保留各自数据、状态、回调及行为，不只做一个示例而让其他同构组继续复制实现。确认旧实现无调用后再清理；范围外的重复项只记录，不擅自迁移。

公共 API 能解释清楚“输入什么、展示什么、回调何时触发”即可。不要为一次卡片复用引入插件系统、全局注册器或通用页面引擎。

## 验证与交付

验证应覆盖共享实现及至少两个实际调用场景（存在多个调用方时），重点检查：

- 公共样式修改能作用到相关入口；没有保留被替代的复制实现。
- 不同参数呈现正确内容，动作触发正确业务方法，稳定 ID 不因排序变化错配。
- 一个实例的选择、加载、错误和分页不会污染另一个实例。
- 长文本、缺图、深浅主题、窄屏与键盘行为适配相关变更。
- 数据获取去重、缓存、取消或竞态行为只在本次改动涉及时验证。
- 若迁移业务方法，核对校验、权限、持久化与失败语义，不能只检查渲染结果。

优先运行已有相关检查；新增测试应证明跨调用方行为或关键回归，不编写只复述实现结构的断言。实际代码变更同时遵守项目的测试、i18n 与注释规范。

交付时简述：复用了哪个基准、哪些调用方已接入、差异通过什么参数注入、哪些业务仍独立及原因，以及实际验证和未验证项。不要把本 Skill 当作全局组件化率指标或无关重构授权。
