# 具体场景与参数契约

本文的组件名和字段是概念示例，不表示当前项目已有同名 API。实施时先查实际组件，不把示例作为创建第二套组件的理由。

## 场景一：以角色库 Card 作为共同视觉基准

用户要求：“这些 Card 都采用角色库 Card，内容与点击行为不同。”

正确路径：找到角色库实际 Card → 判断其业务耦合 → 直接复用或抽取公共展示 → 原角色库和本次其他入口都使用这一份展示。

| 参数类别 | 示例 | 由谁负责 |
| --- | --- | --- |
| 身份 | 稳定 id | 业务适配层，不能用列表下标替代 |
| 内容 | cover、title、description、badges | 业务适配层，不在 Card 内查角色或模型数据 |
| 状态 | selected、disabled、pending | 调用方按各自任务提供，不在模块全局共用一个值 |
| 交互 | onOpen、onSelect | UI 按统一事件契约调用，业务决定后续行为 |
| 动作 | 带稳定 id、标签、禁用状态、回调的 actions | 外部注入动作，公共 Card 统一排版与点击处理 |
| 局部扩展 | footer 等有限插槽 | 只承载真正不同的局部，主体仍共用 |

角色字段映射为展示数据，其他资源也映射为展示数据。两个调用方的打开、删除、收藏可以分别绑定业务方法；共同 Card 不需要知道 `resourceType`，更不应该根据这个字段切换整个业务流程。

如果现有 Card 缺少动作区域，应扩展其明确的动作接口；不要复制一个 `WorkflowCard` 并粘贴原 Card 的 JSX 和样式。若确实需要一个薄业务包装层，它只适配字段与回调，不复制展示结构。

## 场景二：相同参数契约的多个功能组

用户要求：“这些组都是导入相同参数并返回内容，不要一个功能写一套。”

假设组 A 和组 B 的字段结构、校验、调用顺序与返回处理一致，只是默认参数不同，应共享表单/组组件；执行行为也一致时，共用执行方法。

| 公共契约 | 注入差异 |
| --- | --- |
| 统一字段与布局 | 组 id、标题、默认值、当前值、选项 |
| 统一状态表现 | 当前组 loading、error、disabled |
| 统一交互契约 | 参数变更回调、提交回调、结果内容 |
| 统一结果展示 | 由公共模型生成的卡片列表、空态、错误态 |

配置只描述真实差异，不为每组配置一整棵重复 JSX。若一个组多出小块附加内容，使用局部组合；若它的流程、布局已明显不同，复用字段或 Card 等稳定部分即可。

组 A 使用参数甲、组 B 使用参数乙时，必须仍能独立加载、报错和分页。不能为了共用一个 Hook，把所有组强行绑定同一组结果。

## 场景三：内容获取与业务动作分别判断

| 两个功能 | 可以复用 | 必须保留的区别 |
| --- | --- | --- |
| 同一来源、同契约的不同分类列表 | 同一获取函数，分类作为参数 | 分类属于缓存键与请求参数 |
| 不同来源的资源列表 | 已证明相同的分页机制、纯转换、列表 UI | 各自鉴权、请求/响应校验、错误与缓存策略 |
| 删除角色与删除生成记录 | 确认弹窗、按钮状态、相同底层小机制 | 两个删除动作的数据对象、关联清理、存储与通知 |
| 看似相同的“生成”按钮 | 按钮、进度展示和表单公共区域 | 不同工作流的校验、节点映射、执行副作用 |

“返回字段一样”只能支持统一展示模型，不能证明两套获取或写入流程可以完全合并。相同的内容获取机制可以抽取，但不靠一个接受任意 URL 与任意回调的空壳宣称已完成有效复用。

## 边界自检

- 共享组件有多个 `isXxx` 分支，每个分支几乎是不同页面：缩小共享部分，改用组合。
- 各业务只包一层相同 UI，但样式仍分别维护：让调用方引用同一展示组件和样式源。
- 通过 source 参数调用一个巨大 switch，再执行原先各套逻辑：只是搬移重复，继续检查真正共同机制。
- 为复用 UI 把删除、上传、生成、安装都塞入一个服务：恢复业务边界，通过 UI 回调接入。
- 仅找到一个真实调用场景，共性尚不明确：直接实现当前需要，不预建多个假想变体。
- 公共组件已存在却重新造一个“更通用”版本，原入口仍用旧版：先考虑适配或提取原实现，避免形成两个视觉基准。
