# 功能与测试注释规范

遵守根目录 [AGENTS.md](../../../AGENTS.md)。为初级程序员说明代码做什么、为什么这样做和容易踩的坑。

## 不可降低的要求

- **大白话优先，复杂逻辑必须使用生活类比。** 类比之后点明它对应的真实机制，不能代替准确解释。
- **业务代码与测试代码的有效注释率分别不低于 70%，不能互相抵扣。**
- **禁止废话和凑数注释。** 空行、装饰线、复制说明、重复描述，以及“定义变量”“返回结果”“遍历列表”等复述语法的注释不计入。
- 注释必须与行为一致；不为凑比例刻意拆长注释、压缩代码或重复同一解释。

## 统计口径

`注释率 = C ÷ (C + B) × 100%`，C 为有效注释行数，B 为非空代码行数。

- 先确定本次任务的变更基线；工作区已有修改不能全部算作本次成果。新增文件统计全文，修改文件统计本次新增及替换后的行。
- 删除行和未变更上下文不参与统计；补写到函数前的注释只统计本次新增部分。
- 纯注释行有有效内容才计入 C；多行注释按有内容的物理行计，单独的注释定界符不计。JSDoc 也要说明真实契约，不能靠重复类型名称凑数。
- 同一行同时包含代码和注释时只计入 B，避免一行重复计数；非空代码行含 import、类型声明及括号行。
- JS/TS、JSX、CSS 等按各自语法识别注释；独占一行的 JSX 注释容器计作注释行。字符串内的 `//`、URL 或正则内容不是注释。
- 业务代码与测试代码分别汇总；测试夹具、验证和冒烟脚本归测试侧，其他功能辅助脚本归业务侧。
- 仅文档或纯删除且没有可统计的新代码/注释时报告“不适用”，不能把空分母写成 100%。文档示例不算业务或测试源码。

达标关系为 `C ≥ 7B / 3`。例如 30 行代码至少需要 70 行有效注释；数量检查之后仍须人工剔除废话和不准确内容。

## 大白话与类比

| 场景 | 写法 |
| --- | --- |
| 简单逻辑 | 一句话说明业务原因，例如“登录信息还没恢复时先关闭保存入口，避免写入错误账户”。 |
| 算法、数据流或抽象逻辑 | 使用生活类比，例如“把哈希当作文件内容的指纹，再用 Map 按指纹登记，避免同一内容被重复处理”。 |
| 异步、异常和资源清理 | 说明失败后如何恢复、由谁接住异常、哪些资源必须释放。 |

异常说明应准确，例如：“请求失败时在这里提示用户，finally 负责结束加载；超时由请求的超时或取消机制控制。”不能写“不加 try-catch 主进程就会卡死”；try-catch 本身不会让永不结束的请求超时。

## 按需说明的内容

- 模块/函数：职责、关键输入输出、选择该实现的原因与边界；数组和对象说明其业务内容。
- 异步/资源：何时启动、何时取消或释放，哪些状态与持久化会受影响。
- 每个新增或修改的测试：测什么、前置条件、预期结果和失败意味着什么；使用 mock 时说明尚未覆盖的真实行为。
- 界面使用处按根规则标注中文区域名；`"use client";` 保持第一行，文件头说明放在其后。

## 交付前核查

检查注释准确性、类比是否贴切、是否解释边界与清理，以及测试说明是否符合断言。逐文件记录 C、B，再分别汇总业务/测试的注释率；报告统计基线、范围和方法。文本扫描只能给候选数量，未经人工复核不能称为“有效注释率”。

交付简述实现内容、两类统计结果及 1–2 个有效注释示例、实际测试和未验证项。未达 70% 必须明说并继续补足有价值的解释；没跑测试不能写“已通过”。
